## 剧情改成「靠努力推进」（v1.9.0 / schema 6）

**用户指令**：「改成靠努力推进」（选中了我 10-13 给的方案 a）

### 旧逻辑的问题
```js
const wkIdx = Math.floor((weekStart(TODAY()) - st.startWeek) / 604800000);
const chapRaw = wkIdx % chapters.length;
```
- **按时间自动走，不看你做没做** —— 全 App 唯一一个"不劳而获"的系统
- 120 回 ÷ 每周 1 回 = **2 年 3 个月**，孩子不可能读完
- `% chapters.length` 导致第 121 周**绕回第 1 回**，进度从 100% 掉到 0%

### 新逻辑
```js
const CHAPTER_PER_DONE_DAYS = 3;
function storyDoneDays(){          // 累计「军令齐备」的天数
  let n = ST.story.baseDays || 0;  // 迁移折算过来的旧进度
  for(let d = ST.story.startDay; d <= TODAY(); d = addD(d,1))
    if(!isRestDay(d) && isCompleteOn(d)) n++;
  return n;
}
storyChapterRaw() = Math.floor(storyDoneDays() / 3);
storyNextIn()     = 3 - (storyDoneDays() % 3);
```

**关键设计点**
1. **只用累加，永不倒退** —— 撤销记录后进度只可能停住
2. **封顶不归零**：`chapRaw = Math.min(raw, total-1)`，读到第 120 回就停在"全书已读完 🎉"，不再 `%` 绕回
3. **休整日不计入**：`dayIsComplete` 对无任务的日子返回 false，所以休整日天然不算；但仍显式跳过（防「今天想做一点」以外的边界）
4. **补录也推进**：不限于当天操作，任何一天被标记为齐备都会计入
5. 剧情卡右下角从「本周」改成「**再攒 N 天全勤**」—— 给出明确的下一个目标
6. 攒够时弹提示：`📜 主线推进 · 第 N 回「回目」`（延迟 2.9s，避免盖掉上一条"招贤令 +1"）

### 迁移（v5 → v6）
把旧系统已推进的回数折算成 `baseDays = oldChap × 3`，`startDay = TODAY()`，删掉 `startWeek`。
**不让进度倒退** —— 这是这个项目一贯的原则（和账目冻结同一思路）。

### 验证
- 逻辑测试 **120 项**（新增 16 项剧情专项），全绿
- 浏览器测试 **23 项**，全绿
- 截图确认：`已推进 0 / 120 回 · 再攒 3 天全勤`
- 推进速度：120 回 × 3 天 = **360 天满勤**（约一年，且必须真的做才有）

31. **`const total` 与 `viewToday()` 里已有的 `total` 重名** —— 报错 `Identifier 'total' has already been declared`。改名成 `chapTotal` 时**又漏了一处字符串拼接**（转义没匹配上），运行到 `clearRec` 才炸出来。**重命名一定要 grep 全部形态再跑测试。**

## 军功漏洞审计 + 重复武将星级（v1.9.1，未发布）

**用户反馈**：「星星数量好像有点问题，是否有漏洞」+「160 张图鉴他是当宝，非常喜欢」+「抽到重复的良将有一点点失望」

### 审计结论：没有漏洞
新建 `.workbuddy/tests/audit_merit.js`（12 项攻击测试），全过：

| 攻击方式 | 结果 |
|---|---|
| 反复切换同一天战况（30 次） | 军功不变 |
| 开完再关再开（20 次） | 军功不变 |
| 同一锦囊重复开启 3 次 | 只扣一次、只发一张券 |
| 反复渲染 / 反复结算 / 反复补录 | 全部幂等 |
| 同一天重复破敌 10 次 | 令和锦囊都不涨 |
| 军令未了出战 | 被拦 |
| 冻结日与补录窗口重叠 | 不重复计账 |
| 可用 ≤ 累计 | 始终成立 |

**根因说明**：军功不是"记账式"而是"实时重算式" ——
`totalMerit() = earnedMerit() + bonusMerit`，
`earnedMerit() = Σ账本 + Σ活窗口日`，
`liveWindowDates()` 已排除 `settled` 的账本条目，所以两边不重叠。
`setRec` 是纯 setter 不加功；`calcAchievements` 只写日期不发功；
`bonusMerit` 只有两个来源（重复武将折算、迁移补偿）；
招贤令是计数器式（`ticketsEarned() - ST.draws`），`rollDraw()` 唯一调用点紧跟 `ST.draws++`，没有免费抽卡路径。

### 顺手补的纵深防御
`redeem()` 加了 `if(v.redeemed) return` 守卫。界面本来就把「已开启」分到另一区渲染，正常操作刷不了；但函数本身没挡，万一有别的路径调进来会重复扣军功、重复发券。

**用户反馈**：「打卡5天，居然出现1000多星星，不正常」→「我的重点是不要再出错了，正常使用可以吗？」

### 排查过程与结论
建了两个模拟脚本（都可复跑）：
- `.workbuddy/tests/repro_5days.js` —— 全新号 5 天全勤 → **29.4**，正常
- `.workbuddy/tests/stress_30days.js` —— 30 天完整日常（点卯+令牌全用+破敌+开锦囊）→ **442.8**，日均 14.8，正常

**未能复现用户的 1000**。这点如实记录，不装作已解决。

**唯一发现的"突增"是设计使然**：单日最大跳幅 39 = 当日军功 14（7 任务×连击 2 倍）+ 一次稀有重复 25。设计上限约 94（再叠一次传说重复 80，`DUP_MERIT.legend=80`）。

### 定位到真正的「看不出原因」的根因
`bonusMerit` 有三个来源，但军报全标成「**旧将重逢**」：
1. 重复抽到武将折算（6/25/80）
2. 集齐奖励（200/1000）—— v2.0.0 新增
3. 升级补偿（9 位旧武将 × 60）

所以用户看到 1000 也无法从界面判断是哪来的。

### 本版改动
新增 `addMerit(st, n, src)`，src ∈ `dup`/`collect`/`migrate`，三个发奖口全改走它。
军报改为分项显示：`点卯所得 · 旧将重逢 · 集齐奖励 · 升级补偿`。
老数据没有 `meritSrc` 时，差额兜进「**其他**」，不丢数。
