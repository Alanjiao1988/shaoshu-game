## 交付：《我的学习冒险岛》单文件网页应用

**来源**：用户提供小花生网文章（https://mp.weixin.qq.com/s/l6x2Cx887F1R9GLD94cHoQ），花友 @爬坡的小蜗牛 分享用 AI 手搓的儿童学习管理工具。用户选择「做同款工具」。

**产物**：`学习冒险岛.html`（1779 行，96 KB，零外部依赖，可离线双击运行，数据存 localStorage key `study_island_v1`）

### 功能实现
- **滑动窗口任务**：弹性任务按「每周目标次数」计，不产出欠债记录；只提示「还差 N 次」；提前达标当天从列表消失并进「提前放假」列表；支持「跳过今日」顺延
- **四档星级**：完整高质量=1 星 / 尽力了=0.5 星 / 质量不达标=0.5 星 / 没动手=0 星。半星算作「已做」，可触发当日完成
- **奖励双轨**：抽奖券（当日全部完成 +1，击败 BOSS +2）；星星（打卡累计，兑换奖品时扣减）。星星余额 = 累计 - 已兑换
- **盲盒**：三档奖品（普通/稀有/传说），权重可调；奖品先进「奖品库」，攒够星星门槛才兑换；同门槛可调换
- **BOSS 战**：7 套形象按星期轮换，血条 = 未完成任务比例，当日全清才能攻击
- **其他**：六大视图（今日/一周/奖品库/数据/周报/设置）、能量树（完成率→20 片叶子）、计划vs实际用时对比、8 级赛季称号、8 个成就徽章、节日皮肤（春节/中秋/国庆/儿童节/圣诞）、任务与奖品 CRUD、JSON 导出导入、示例数据生成

### 验证
- Node 无头逻辑测试 54 项全通过（滑动窗口、星级、券结算、BOSS 判定、抽奖分布、持久化容错、节日皮肤）
- 真实 Chrome（CDP 驱动）UI 交互测试 63 项全通过，覆盖打卡全流程、BOSS 战、盲盒、六视图渲染、任务 CRUD、周报保存、奖品兑换、翻周导航、空数据与未来日期容错
- 桌面端 + 移动端（390×844）截图视觉确认

### 踩坑记录（下次做类似事直接复用）
1. `String.replace(str, replacement)` 的**替换串**里 `$$` 会被转义成 `$`、`$&` 会被展开。注入脚本时必须用函数式替换 `replace(a, () => b)`，否则代码被静默改写。这次导致 `var $$` 覆盖 `var $`，排查花了很久。
2. Windows 上 Chrome 是 GUI 子系统进程，Git Bash / execFileSync 抓不到 `--dump-dom` 的 stdout。可靠做法：起本地 HTTP 服务 + `--remote-debugging-port` + Node 内置 WebSocket 直连 CDP，用 `Runtime.evaluate` 取结果、`Page.captureScreenshot` 截图。
3. 残留的 chrome.exe 会占着固定的调试端口，新起的 Chrome 绑不上端口，CDP 会连到**旧浏览器里的旧页面**，导致测试结果像是「代码没更新」。必须用随机端口 + URL 带 run id 校验。
4. 打开的 WebSocket / HTTP server 句柄会让 Node 进程不退出，脚本末尾要显式 `process.exit()`。
5. Windows 下 Chrome 退出后仍锁定 user-data-dir，`rm -rf` 静默失败；下次复用同一目录会命中磁盘缓存拿到旧页面。每次用唯一 profile 目录 + `Cache-Control: no-store`。
6. 用 `vm` 跑无头逻辑测试时，凡是依赖 `Math.random` 的用例必须临时固定随机数（`withRandom`），否则会偶发失败。第一次跑 82/1、第二次 83/0 就是这么来的。
7. 测试断言要写成**相对**的（"解锁后 locked 减少 2"），不要写死的绝对值（"locked === 34"）。前序用例有随机性时，绝对断言必然翻车。

## 三评：对《少年主公》的缺口分析（只分析未改动）

用户问「还有什么可以完善」，第一次给的是"修 bug + 加功能"清单，用户明确说「远远不够」。第二次重新想，得出三个层面判断。

### 已实测复现的账目缺陷（4 条，只读模拟，未改代码）
1. **招贤令被追溯撤销**：孩子三天军令齐备得 3 枚券 → 家长新增一项每日军令 → 那三天 `dayIsComplete` 全部翻成 false → 券变 0 枚
2. **军功倒退**：`delTask` 会连历史 records 一起删；实测累计军功 6 → 3
3. **官职掉级**：军功 520「校尉」→ 430「军侯」
4. **历史被改写**：弹性任务"本周已达标撤下"是动态算的，改 weekTarget 会让过去某天的状态翻转
5. 附带：`availMerit()` 里的 `Math.max(0,...)` 会把军功负值悄悄吞掉

**根因**：所有奖励都是**实时重算**（`ticketsEarned()` 遍历历史日期重新判定、`earnedMerit()` 对 records 求和），不是**记账**。童话版这么做没错（只有打卡本身），但三国版引入了军功/招贤令/官职这些"要兑现的资产"，性质就变了 —— 资产必须是账本。

### 三个层面的结构性判断（比 bug 更重要）

**A. 重心偏了：原文的重心是「记录」，我做成了「奖励」**
原文原话：「工具的本质，只是把孩子每一天实实在在的努力记录留存下来，不要让孩子只记住'我又没完成任务'。」
实测统计：招贤榜/武将图鉴/锦囊匣/官职/10徽章/点将台/破敌 ≈ 全部是奖励；"记录"只有周报 + 点将台，且都只看得见本周。
风险：外在激励会腻（抽卡腻了、奖品换完了），内在动力（看着自己变强）才持久。数据页全是**本周**视角，看不到长期成长曲线。

**B. 最大的功能缺口：家长端诊断能力**
原文那个妈妈真正的动作是「观察 → 判断 → 调整」（例：英语阅读从每周 4 篇调到 2 篇）。工具应把这个过程自动化：某项连续多周完成率过低 → 主动建议调周目标或换时间点。
现在数据页全是给孩子看的（点将台、徽章、官职），**没有一个给家长看的诊断视图**。这恰恰是它相对纸质表格的核心优势。

**C. 缺「协商」这个载体**
原文反复强调"规则是我们一起商量出来的"。我把这些塞进了「设置」页 —— 那是单方面配置，不是协商。缺一个每学期开学时家长和孩子一起过一遍所有可调项、生成「本季约定」的界面。
她不是在做工具，是在做协商机制。

### 其他缺口（按层面）
- **机制层**：没有目标层（任务之上无目标，沦为交易）；没有累积总账；只有"周"这一种节律，缺期中/期末节点；`TODAY()` 用本地时间，23:50 打卡 + 0:10 继续会记成两天（需要一个"一天从凌晨几点算起"的设置）；错点无法撤销
- **激励层**：玩法会腻（那位妈妈自己预言"下学期可能没新鲜感"）→ 应做玩法可插拔；「苦战」的价值观没被突出（文章最动人的是"这是我当初差点放弃的那半颗"，现在只是 10 个徽章之一）；奖励池会通胀，攒满最高门槛后没目标了
- **数据层**：两年数据在 localStorage，清缓存全没 → 需要自动快照 + 导出提醒；无版本迁移机制

### 如果只做三件
1. 家长诊断视图（每周自动给一句「建议」）
2. 目标层（任务之上加目标）
3. 记录沉淀（跨周曲线 + 累计总账）
理由：都是把重心从"奖励"拉回"看见成长"。

## 四改：按「强驱动」方向落地第一组改动（已实施）

**用户决策**：「推着孩子走」——强外在激励路线。选定范围：零副作用那一组（清晰化下一步 + 反馈密度 + 连击 + 保底 + 毕业机制）+ 账目冻结。

**产物**：`少年主公.html` 现 2521 行 / 119KB，仍零依赖。localStorage key 未变（`shaozhu_v1`），老数据自动兼容。

### 一、账目冻结（修掉 4 处会倒扣的缺陷 + 2 处连带问题）
新增 `ST.ledger`：每一天一经结算就写死 `{tasks快照, done, total, complete, base, mult, merit, ticket}`，之后永不再算。

- `settleLedger()` 在**每次启动**和**任何任务增删改之前**调用
- **踩坑**：最初只遍历「有打卡记录的日子」，结果空白日子（当天没打开、一个字没记）没被冻结，改周目标仍会改写历史。必须从 `ST.createdAt` 起逐天推进到昨天
- `tasksForDate()` / `holidayTasks()` 对已结算日期直接返回账本快照 → **历史的样子也被冻结**，不光是数字
- 账本存的是**任务快照**而非 id，所以军令改名或删掉后，历史仍按原样呈现
- `earnedMerit()` = 账本求和 + 今天的实时；`ticketsEarned()` = 账本累加 + 今天实时的 1 枚 + 破敌×2
- 官职改用 `rankMerit()` = max(当前, `ST.peakMerit`)，只升不降
- 去掉 `availMerit()` 里掩盖亏空的 `Math.max(0,...)`
- **今天绝不写入账本**（要保持实时，孩子当场能看到变化）
- **新增设计决定：已结算的历史只读**。`openCheck` 对已结算日期改跳只读详情页；`clearRec` 拒绝执行。原因：允许改会牵动军功、招贤令、连击、周报，越改越乱；而且"不追究前日之失，也不能回头改写前日之功"

### 二、把「下一步」说清楚
`nextStepHint()` 四态：还有未完成 → "再做 N 项军令即可破敌，胜可得 🎟️×2"；全清未破敌 → "军令已齐，曹操就在官渡！"；已破敌 → "再攒 N 军功升「中郎将」"；无军令 → 安静。只对**今天**显示，看历史/未来日期不显示。

### 三、连击倍率
`STREAK_TIERS`：连续 3 天 ×1.2（渐入佳境）/ 5 天 ×1.5（连战连捷）/ 7 天 ×2（势如破竹）。倍率在**结算那一刻**烧进账本的 `merit`。顶栏 ≥3 天才显示 🔥 徽记。

### 四、抽卡保底
`PITY = 20`，`ST.pity.sinceLegend`。**出锦囊也算累积**。满额时 `pickLegend()` 强制出神将且优先未获得的。进度在武将页和招贤榜弹窗都可见 —— 可见的保底进度本身就是推力。

### 五、毕业机制（退场设计，本次最关键的一条）
`GRADUATE_WEEKS = 4`：连续 4 个**完整周** 100% 达成 → 自动移入「已养成」荣誉墙（`t.archived=true` + `ST.graduated`），可一键恢复。周目标只有 1 次的弹性任务不算习惯，排除。毕业时弹 🎓 庆祝页，文案落在「推着走的终点，是你自己走」。荣誉墙在数据页最底部，空态也写了一样的说明。

### 六、反馈密度
- 点卯后从被点选项位置飘出 `⭐ +1` / `◑ +0.5`（`floatFromEl` + CSS `@keyframes floatUp`）
- 整日齐备时撒花 + 连击提示 toast
- 每日首次打开弹「今日军令已下达」仪式卡（`ST.lastOpen` 控制），内容是军令清单 + 连击 + 下一步
- 设置页新增「补发招贤令」，方便立刻试揭榜

### 验证
- 逻辑测试 **67 项全通过**（含 6 条专门盯账目冻结、8 条连击、6 条保底、8 条毕业）
- 真实 Chrome UI 交互测试 **93 项全通过，连跑 2 次稳定**
- 桌面 + 移动端截图确认（今日提示条 / 仪式卡 / 毕业庆祝 / 招贤榜保底进度 / 荣誉墙）

### 新增踩坑
11. **`settleLedger` 不能只遍历有记录的日子** —— 见上。这是"冻结"能真正成立的前提。
12. 测试断言要放在正确的状态点。我两次把"连击应为 1"写在了当天还没完成的时候。
13. 冻结之后，"断掉一天连击归零"这类断言不再成立 —— 因为那天已成为不可改写的历史。这时要回过头问自己：**这是 bug 还是设计**？答案是设计，于是补上了只读详情页和拒绝逻辑。

## 五改：iPad 适配（已实施）

**用户问**：这个能在 iPad 上吗？

**查证结论（有出处）**：
- iPadOS「文件」App 用 Quick Look 预览 HTML **不执行 JavaScript**
- iOS Safari 没有"打开本地文件"入口，也不出现在文件的"打开方式"里（iOS 18 起进一步收紧）
- **WebKit 在 `file://` 协议下强制禁用 localStorage / sessionStorage / IndexedDB**（安全策略，非 bug）
- 结论：**本地双击打开这条路走不通**，必须走 HTTP(S)

**可行路径**：① 发布成网址，Safari 打开后「分享 → 添加到主屏幕」，全屏运行；② 第三方 App（Documents by Readdle / iCab Mobile / Server for PHP）自带 WebKit 或本地服务器

### 本轮改动
1. **PWA meta**：`apple-mobile-web-app-capable`（加到主屏幕后全屏）、`apple-mobile-web-app-title`、`mobile-web-app-capable`、`theme-color`、内联 data-URI manifest
2. **安全区**：body 补 `env(safe-area-inset-left/right)`（底部原本就有）
3. **触摸优化**（`@media (pointer:coarse)`）：
   - `.btn` 提到 44px、`.opt` 60px、`.btn.sm` 36px（Apple 触控建议）
   - **`textarea/input` 字号提到 16px** —— iOS 对 <16px 的输入框会自动放大整页
   - `touch-action:manipulation` 去掉双击缩放延迟
   - `-webkit-text-size-adjust:100%` 防横屏字号膨胀
   - 点按回馈加强、列表项间距放松
4. **存储告警条**（`#storageWarn` + `storageAvailable()` + `checkStorage()`）：localStorage 不可用时在页面顶部亮红条，说明原因并给出替代方案；`save()` 失败时也会点亮它；仪式卡在存不住时不弹，避免遮住告警

### 踩坑（第 14 条，很典型）
**`@media (pointer:coarse)` 写在样式表开头会完全失效** —— 它和组件层选择器同优先级，会被后面定义的 `.btn{min-height:40px}`、`input{font-size:13.5px}` 直接覆盖。触摸优化整块一条都没生效，而 `pointer:coarse` 本身是匹配的（`matchMedia` 返回 true），所以极难从表象发现。**必须把设备专项覆盖放到样式表最末尾。** 这是靠 iPad 模拟实测才发现的。

## 六评：上线后的缺口分析（只分析，未改代码）

用户第三次问「还有哪里需要改进」。之前已覆盖（不重复）：家长诊断、目标层、跨周曲线、协商载体、玩法轮换、自动备份、学期节点、深夜跨日、撤销历史、敌我身份、概率公示、键盘操作。

### 本轮新识别（按严重度）

**S 级 —— 架构缺陷**
1. **奖励兑现没有闭环**。链路「点卯→军功→开锦囊→找大人兑现」在第 4 步断掉：工具只发一句 toast，不记录孩子提了什么要求、家长有没有做到。**一次不兑现 → 孩子判定"军功没用" → 整条链反向运转**。隐性失效：界面看起来一切正常，驱动力在漏。修法：开锦囊生成带编号日期的「兑现券」，家长点「已兑现」才闭环；统计兑现率；逾期提醒。
2. **上线后的运维问题**（这是本轮新增的问题类别，文件变产品后才存在）：
   - 无 service worker → 断网打不开
   - **界面无版本号** → 用户无法确认用的是新版还是缓存旧版
   - 无版本驱动的数据迁移，全靠 `load()` 里逐字段 if 兜底，撑不过第三次改结构
   - 链接公开（数据仍在本地），未来做云同步/分享需重新评估隐私边界

**A 级**
3. **没有休假模式**。工具默认"每天都能完成"，但孩子会生病/期末周/寒暑假/没带 iPad。这些日子照常生成任务、照常算 0%。应支持「休整期」：不生成任务、**连击冻结而非清零**（病三天回来发现连击断了是最不该受的打击）。
4. **只会推不会退**。六种推力 vs 一种退（免战牌）。难度闭环缺两头：连续 2 周 <40% → 建议降目标；完成率 100% 但全半星 → 说明在赶，建议换时间点。只有中间的"毕业"做了。
5. **衡量指标全错**。现在全是「完成度」，但真正的目标是「主动性」（原文妈妈最惊喜的正是"从被动到主动"）。可测但没测：主动打开次数、主动要求加任务、提前完成次数、自己调目标次数。**完成率可以靠推，主动推不出来。** 建议周报加一行"本周孩子主动做的 N 件事"。
6. **孩子在系统里没有嘴**。只有"点卯"一个动作。原文那个孩子做了三件：点卯、参与定规则、主动要求加任务。可先加三个按钮：「再给我加一项」「这项太难了」「我想要这个奖品」——最后一条把"家长猜孩子想要什么"变成"孩子自己说的"。

**B 级**
7. 累计总账（"我走了多远"），《三国演义》120 回进度是现成的载体
8. 备份提醒（导出是手动的，忘了就没了）
9. 多孩支持（两个孩子要开两份数据互导）
10. 期末成长报告（可导出/打印）
11. iPad 横屏时周视图不必要地横向滚动（1024px 够宽，只有 768px 竖屏才需要）

## 八改：3 天补录窗口（已实施）

**用户决策**：「要加」。

**产物**：`少年主公.html` v**1.5.1**，schema **3**。`site/sw.js` 的 `VERSION` 同步改为 1.5.1。

### 设计
原来「一旦结算就永久冻结」把"昨天忘了点卯"也一起锁死了。现在改成一条更好懂的规则：

> **最近 `BACKFILL_DAYS`（=3）天含今天，账还没冻结，可以补录；更早的日子一经结算就只读。**

- `backfillFloor()` = `addD(TODAY(), -(BACKFILL_DAYS-1))` → 窗口 = [今天-2, 今天]
- `isFrozen(d)` = `d < backfillFloor()`
- `canBackfill(d)` = `!isFrozen(d) && d <= TODAY()`
- `settleLedger()` 只结算 `< backfillFloor()` 的日子，窗口内的留活口
- **`liveWindowDates()`**：窗口内尚未结算的日子要实时算进 `earnedMerit()` / `ticketsEarned()`，否则刚补的点卯不认账 —— 这是本次最容易漏的一处
- `openCheck` / `clearRec` 的只读判定从 `dateStr<TODAY()` 改为 `isFrozen(dateStr)`
- `calcAchievements` 的完美一周判定同样改用 `isFrozen`

### 迁移（v2 → v3）
按 schema 逐级升的机制第一次派上用场：**把落在窗口内的账本条目删掉**，让老数据一升级就立刻获得补录能力。
```js
if(s.schema < 3){
  const floor = addD(TODAY(), -(BACKFILL_DAYS-1));
  for(const d in s.ledger){ if(d >= floor) delete s.ledger[d]; }
  s.schema = 3;
}
```

### UI
- 日期栏上，窗口内未完成的日子显示 ✍️ 标记
- 查看窗口内的过去日期时，顶部出现「✍️ 这一天还可以补录 —— 还有 N 项没点卯」
- 只读详情文案补上「（只能是最近 3 天内补录）」

### 代价（已向用户说明）
窗口内那 3 天是"活的"，所以**家长在这 3 天内改任务，会影响到这几天的完成状态**。3 天很短，可以接受；窗口之外的冻结保证完全不变。

### 验证
- 逻辑测试 **81 项**（新增 12 条补录窗口用例），连跑 3 次全绿
- 浏览器 UI 测试 **73 项**，连跑 2 次全绿
- Service Worker 已激活，缓存自动升级为 `shaozhu-v1.5.1`
- 截图确认补录界面（日期栏 ✍️ 标记 + 顶部提示条）

### 本轮踩坑
18. **vm 沙箱里的 `ST` 在 Node 作用域访问不到**，测试里写 `delete ST.records[...]` 直接 ReferenceError。必须走 `run('delete ST.records[...]')`。
19. 测试断言里手写选择器漏了引号（`$(".boss-card)")`），直接抛异常把整个测试主体打断 —— 这种低级错误会因为"主体异常"而掩盖后续所有用例，写断言时要格外小心。
